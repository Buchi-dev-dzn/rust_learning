# 卒業課題の進め方

第1〜22章で学んだ Rust とターミナル開発の知識を、七つの卒業課題で組み合わせる。卒業課題は完成品を眺めるだけでなく、**仕様を読み、テストを失敗させ、少しずつ通す**練習だ。

## ファイルの役割

各課題の `finals/<id>/SPEC.md` が公開 API と境界条件を定める。`HINTS.md` は `---` ごとに段階的に読むヒント。`src/` が編集する初期状態で、`tests/acceptance.rs` は変更しない。解答は `course/finals/<id>/solution/src/`、初期状態のバックアップは `course/finals/<id>/starter/src/` にある。

```text
finals/f3_keyparser/
├── Cargo.toml
├── SPEC.md
├── HINTS.md
├── src/                 ← 学習者が編集
└── tests/acceptance.rs  ← 合格条件・変更しない
course/finals/f3_keyparser/
├── starter/src/         ← 初期状態と完全に同じ
└── solution/src/        ← 模範解答
```

最初のテスト失敗は正常だ。`todo!()` は Rust としてコンパイルできるが、呼ぶとパニックする。テストが通らない状態から始まり、最後に `cargo test -p <id>` を成功させる。

```sh
cargo build -p f3_keyparser
cargo test -p f3_keyparser
cargo test -p f3_keyparser --test acceptance
cargo test -p f3_keyparser --test acceptance -- <テスト名>
```

エラーが **コンパイル失敗** なのか **アサーション失敗** なのかを区別する。コンパイル失敗なら型・所有権・借用と公開 API の綴りを確認しよう。アサーション失敗なら実際の値と期待値、境界条件を確認する。新しい関数を実装する前に、SPEC の該当箇所とテストを対にして読む。

## 七つの課題

| ID | 内容 | 主な技術 | 判定 |
|---|---|---|---|
| F1 `f1_coreutils` | wc / cat / head | std::io、CLI 引数 | 出力と終了コード |
| F2 `f2_ls` | カラー対応 ls | ファイルシステム、Unicode 表示幅、ANSI | 整形ロジック |
| F3 `f3_keyparser` | キー入力パーサ | 増分バイト列解析、エスケープシーケンス | パーサ |
| F4 `f4_diff_renderer` | 差分レンダラ | セルバッファ、ANSI | 生成シーケンス |
| F5 `f5_editor_core` | エディタのコア | テキスト構造、Undo | 編集操作 |
| F6 `f6_sysmon` | htop 風モニタ | スナップショット、イベントループ、ratatui | 状態更新ロジック |
| F7 `f7_file_manager` | 自作フレームワークのファイルマネージャ | libc、Widget、レイアウト | ウィジェット / レイアウト |

F1/F2 はコマンドとファイル、F3/F4 は入力と描画、F5 は編集操作、F6/F7 は実際の TUI につながる。難しい課題を先に覗いて「何のための技術か」を確かめ、まず小さな課題から仕上げてもよい。

### F1: コマンドラインの約束

標準入力・ファイル・複数ファイルをどう扱うかを SPEC で調べる。正常系だけでなく、読めないパス、無効なオプション、空ファイル、改行なしの最終行も確認しよう。CLI では正しい文字列を表示するだけでなく、標準出力と標準エラー出力、終了コードが契約になる。`std::process::Command` で実行するテストは、利用者の目線そのものだ。

### F2: 文字数と表示幅

`read_dir` の列挙順をそのまま表示すると、環境によって結果が変わる。名前や種類のソートを先に決める。文字列のバイト長と見た目の幅は異なる。たとえば日本語 1 文字は UTF-8 では複数バイト、端末では通常 2 セル。整形用の列幅を決める関数を分離し、色の ANSI シーケンスは列幅に含めない。色を無効にした場合の結果も比べよう。

### F3: 増分パーサ

端末からの `read` は「ちょうど 1 キー分」を返す保証がない。UTF-8 文字が途中で切れたり、矢印キーの ESC シーケンスが複数回に分かれたりする。入力バイト列と内部の保留バイト列を別に持ち、イベントが確定するまで待つ。単独 ESC をどう確定するか、無効バイトをどう扱うかは SPEC の規則に合わせる。

### F4: 二枚の画面

現在のセルバッファを組み立ててから、前回のセルバッファと比較する。変更セルだけ ANSI を出すので、無変更のフレームは画面全体を塗り直さない。幅 2 の文字は右半分を独立した文字として出力しない。行・列は ANSI では 1 始まり、Rust の添字では 0 始まりであることに注意する。

### F5: Undo は編集履歴

単に文字列を戻すだけではカーソル位置が失われる。編集前のテキストと位置を記録し、どこまでを 1 グループにするかを決める。連続入力、空白の後、移動後、削除後などの境界をテストしよう。`String` の切り出しにバイト位置を使う場合、カーソルの文字位置から境界を変換する必要がある。

### F6: テスト用スナップショット

実際の CPU 使用率やプロセス数は実行するたびに変わるため、そのまま受け入れテストに使えない。`Snapshot` を組み立てて `App::update` に渡し、ソート、絞り込み、選択維持、履歴容量を決定的に確認する。描画・取得スレッドと状態更新を分ければ、同じ状態を何度も再現できる。

### F7: フレームワークを組み立てる

`Rect` で領域、`Buffer` でセル、`Widget` で描画規約を定める。ファイル一覧はその上に載せる一つのアプリだ。親ディレクトリへ戻るときに以前いた子を選び直す、空ディレクトリでも移動が安全、狭い画面でも座標計算が壊れない、といった場面を先にテストする。端末 I/O の前にバッファの一行を文字列として検証すると、問題を切り分けやすい。

## 仕様を先に分解する

例えば「選択を維持する」という要件は、そのままだと曖昧だ。並び替えの前に選択中の PID を覚え、新しい一覧から同じ PID を探し、なくなれば index を末尾で丸める、と分割できる。空一覧のとき index は 0。ここまで決めるとテスト可能になる。

```rust
// 端末を起動せず、状態の変化だけを確認する例。
fn clamp_selection(index: usize, count: usize) -> usize {
    index.min(count.saturating_sub(1))
}

fn main() {
    assert_eq!(clamp_selection(10, 3), 2);
    assert_eq!(clamp_selection(10, 0), 0);
}
```

入力パーサも「キーを読む」ではなく、1 バイトずつ与えたときに `None` を返す時点と、イベントを確定する時点を決める。文字列処理なら UTF-8 のバイト位置と文字位置を混同しない。全角表示なら文字数と端末セル数は違う。SPEC の表と例をそのまま小さなチェックリストにしよう。

## 実装順序の例

1. `SPEC.md` の公開 API を `src/lib.rs` に揃える。変更するのは最初は小さな関数一つだけ。
2. `cargo build -p <id>` で型と借用を確認する。
3. 対応する受け入れテストを一つ実行し、成功・失敗の理由を読む。
4. 境界 (空入力、範囲外、Unicode、EOF、末尾) を確認する。
5. 次の API に進み、最後にパッケージ全体のテストとビルドを行う。
6. 完成後、解答と自分の設計を比較する。解答と同じコードである必要はない。

`HINTS.md` の最初の段は考え方、最後の段は実装方針に近い。すぐ解答をコピーするより「このテストを通すために何が足りないか」を説明できることを目標にする。

## 端末 UI とロジックを分ける

F6/F7 では `lib.rs` が状態と描画ロジック、`main.rs` が実際の端末 I/O を担当する。受け入れテストは端末を開かずにライブラリを呼ぶ。CI や IDE に対話端末がなくてもロジックは検証できる。

F6 は取得した `Snapshot` を注入して並び替え・フィルタ・履歴を検証する。実際の `ps` 実行、スレッド、ratatui の描画は `main.rs` に置く。F7 は自分の `Rect`、`Buffer`、`Widget` を組み合わせ、端末の raw モードや `poll` を `main.rs` に隔離する。

```rust
// テスト可能な状態と、端末への副作用は別の層に置く。
struct State { selected: usize, len: usize }
impl State {
    fn down(&mut self) {
        self.selected = (self.selected + 1).min(self.len.saturating_sub(1));
    }
}
fn main() {
    let mut state = State { selected: 0, len: 2 };
    state.down();
    assert_eq!(state.selected, 1);
}
```

TUI を起動するなら対話端末で `cargo run -p f6_sysmon` または `cargo run -p f7_file_manager` を使う。終了キーを先に確認し、アプリを抜けたとき raw モード・代替スクリーン・カーソル表示が元に戻ることも確認する。パニック時に復元するフックや Drop ガードは見た目以上に重要だ。

## よくあるエラー

- `mismatched types`: `Option<T>` や `Result<T, E>` を `T` と取り違えていないか。空一覧や読み取り失敗の動作を SPEC で確認する。
- `cannot borrow ... as mutable`: 参照を保持したまま一覧を変更していないか。選択キーを先にコピー・複製してから更新する。
- `index out of bounds`: 空の一覧で `len - 1` をしていないか。`saturating_sub(1)` が役立つ。
- テストの文字位置が違う: `String::len()` は UTF-8 のバイト数。`chars().count()` と、必要なら `char_indices()` を使う。
- ANSI の期待値が違う: 色・カーソル移動・リセットの順序を確認し、変更がないセルまで出していないかを見直す。

## テストから仕様を読み取る練習

受け入れテストは、関数の戻り値だけでなく「呼び出す順番」も示す。例えば `update` → `set_sort` → `selected_process` のテストは、並び順が変わっても同じ対象を選べるかを調べている。単独の関数ごとには正しくても、連続操作で状態が壊れることがある。

テストを読むときは次をメモする。

- **初期条件**: 空の一覧か、複数の要素があるか。
- **操作列**: 一度だけ呼ぶか、続けて何度も呼ぶか。
- **観測点**: 戻り値、状態、標準出力、標準エラー、終了コードのどれか。
- **端点**: 最初・最後・空・満杯・範囲外を試しているか。
- **不変条件**: 行数は 1 以上、選択位置は表示リストの範囲内など。

期待値を合わせるためだけに特殊分岐を増やすのではなく、不変条件を保つ設計にする。たとえば空一覧の位置は 0、追加や削除の後は `min(index, len.saturating_sub(1))` とすれば、多くの操作が同じ規則を共有できる。

## 小さな追加テストを自分で書く

受け入れテストは必要条件を確認するが、全入力を列挙しない。自分の実装が怪しいと感じたら、ローカルに小さな単体テストを追加できる。ただし `tests/acceptance.rs` 自体は変更しない。`lib.rs` の末尾に `#[cfg(test)]` のモジュールを置く方法がある。

```rust
fn bounded_next(current: usize, count: usize) -> usize {
    current.saturating_add(1).min(count.saturating_sub(1))
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn empty_list_keeps_selection_zero() {
        assert_eq!(bounded_next(0, 0), 0);
    }
    #[test]
    fn stops_at_last_item() {
        assert_eq!(bounded_next(2, 3), 2);
    }
}

fn main() {
    assert_eq!(bounded_next(0, 2), 1);
}
```

この例は標準ライブラリだけで完結し、実行ボタンでも動く。実際の課題では公開 API の関数名と型に合わせてテストを書く。再現したい入力が見つかったら、どの不変条件に反しているかを先に説明してから修正する。

## エラー処理と所有権の設計

F1 のコマンドは読み取り失敗を終了コードに変換する。F7 のディレクトリ遷移は `io::Result` として呼び出し側に返し、画面ではエラーをメッセージにできる。エラーを `unwrap()` で隠すと、端末の復元処理や利用者への案内も失われかねない。

状態を置き換える操作では「読み取りが成功してから変更する」という順番を守ると安全だ。先に現在パスを変えてから `read_dir` が失敗すると、表示と実際のパスが食い違う。次の状態を一時変数に作り、成功したときだけ代入する。

```rust
use std::fs;
use std::io;
use std::path::Path;

fn file_count(path: &Path) -> io::Result<usize> {
    let mut count = 0;
    for entry in fs::read_dir(path)? {
        entry?;
        count += 1;
    }
    Ok(count)
}

fn main() {
    let path = std::env::temp_dir();
    let _ = file_count(&path); // 対話入力も端末操作も必要ない
}
```

`?` は読み取りエラーを呼び出し側に伝える。`read_dir` 自体が成功しても、反復中の各 `entry` がエラーになる可能性がある。何を無視し、何を呼び出し側に伝えるかを仕様に合わせて決めよう。

## 完了後のセルフレビュー

- 公開 API の名前・型・戻り値が SPEC と一致しているか。
- 文字位置、バイト位置、表示セルの幅を混同していないか。
- 空入力と読み取り失敗の両方で安全に動くか。
- starter がコンパイルし、受け入れテストが本当に失敗するか。
- 解答を試すと受け入れテストがすべて成功するか。
- TUI を開いた場合、`q` などで終了し端末が元に戻るか。
- 自分で書いたテストが受け入れテストと矛盾しないか。

学習用の `src/` を解答で上書きして動作を比べる場合は、初期状態を先に退避する。比較が終わったら starter に戻し、次に課題に取り組む人が失敗から始められる状態にする。

## まとめ

卒業課題の合格は「指定された振る舞いを、公開 API と受け入れテストの両方で満たした」ことを意味する。端末を使う課題でも、まず純粋なロジックのテストを確実に通そう。その後で実際に起動し、見やすさ・操作感・異常時の端末復元まで自分で確認する。ここから先は自分のターミナルアプリを設計する番だ。
